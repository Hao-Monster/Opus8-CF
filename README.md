# Opus8-CF

一套把「多账号批量部署的分散 Cloudflare 边缘节点」和「统一控制面 + 按用户鉴权 + 订阅下发」缝合起来的
代理分发平台。设计目标见 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

## 形态

- **数据面 `packages/edge-node`** — 增强版 edgetunnel（生产下发 VLESS-WS，保留 XHTTP · ECH · TLS分片 ·
  proxyIP/NAT64 · 可切换 SOCKS5 落地分流），多账号批量部署；gRPC 已在构建产物中禁用。
- **控制面 `packages/control-plane`** — Worker + D1 + KV：节点/用户注册表、订阅生成、UUID 同步总线、Admin API。
- **管理站 `packages/admin-ui`** — Cloudflare Pages（React/Vite），GitHub 自动部署。
- **编排 `.github/workflows` + `infra`** — 多账号矩阵部署、优选 IP、健康自愈。

## 部署

所有凭据存于 GitHub Actions Secrets；部署经由 CI。见 [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md)。
先跑 **preflight** 工作流验证密钥、创建 D1/KV、探测落地机端口。

节点部署不会读取控制面根密钥或管理员密码。手动运行 `deploy-nodes` 时，每个账号 Job 会用窄权限 HMAC 自动化身份
即时创建一次性注册任务，绑定 Node ID、账号别名、域名和传输路径，部署验证完成后自动收回旧凭据。
管理站“节点管理”也可生成同样的一次性令牌，供单机部署或故障恢复使用；令牌只显示一次。
P6.10 的发布顺序、Secret 配置和新增账号步骤见
[`docs/P6.10-OPERATIONS-HARDENING.md`](docs/P6.10-OPERATIONS-HARDENING.md)。新 Cloudflare 账号从 Token、
Secrets、声明式拓扑到首次 canary 的完整步骤见
[`docs/NEW-CLOUDFLARE-ACCOUNT-NODE.md`](docs/NEW-CLOUDFLARE-ACCOUNT-NODE.md)。

## 落地分流运维

- 管理站的“落地分流”页面可在线增删域名；规则保存在控制面 KV，节点约 15 秒内自动更新，无需重新部署。
- 管理站的“落地机”页面可维护多台 SOCKS5：地址、端口、用户名、密码、地区、优先级和负责域名。
- 负责域名留空表示默认落地；同一域名可由多台落地机负责，数字较小者优先，连接失败自动尝试下一台。
- 落地机密码不会回显；凭据在 D1 中由 `LANDING_CONFIG_KEY` 使用 AES-GCM 加密，节点仅接收用节点密钥再次加密的运行时配置包。
- 用户只有开启“解锁”权限后，命中清单的目标域名才会走 SOCKS5 落地；其他流量使用 CF 直出。
- 代码默认值维护在 `infra/ai-unlock.txt`。修改并推送该文件会依次触发控制面和节点部署。
- 域名按“根域名或其子域名”精确匹配，不使用正则模糊后缀，避免 `evil-example.com` 误命中 `example.com`。

## 防分享与流量

- 每台设备拥有独立订阅令牌和连接凭证；新设备使用 HMAC-SHA256 派生的 24 小时动态 UUID，并同时接受上一时间窗，兼容客户端定时更新。升级前的设备保持静态 UUID，管理员可手工“轮换凭证”完成迁移。
- HWID 是可选增强项：`off` 完全兼容标准客户端，`optional` 在客户端提交 `x-hwid`/`x-hwid-device-id` 时执行软绑定，`required` 要求首次下载即绑定。D1 只保存按设备域隔离的 HMAC，不保存原始硬件标识。
- 默认允许同一订阅同时使用 2 个公网 IP、24 小时内使用 5 个公网 IP；可在“用户与防分享”页面逐用户调整。
- 控制面按用户派生稳定且不可逆的 IP 指纹密钥；不同节点对同一用户生成一致指纹，D1 不保存客户原始公网 IP。
- IP 准入对全部用户保留；只有设置了正流量额度的用户才在生产节点按设备 UUID 分批、幂等汇总字节到 D1。用量批次会根据剩余额度在 256 KiB–8 MiB 间自适应，并在接近额度时缩短刷新间隔；控制面将一次上报中的事件合并写入小时汇总。不限量用户不创建精确用量事件，以降低 Worker/D1 压力。
- gRPC 已放弃：Zone 开关保持关闭，Worker 对 gRPC 请求返回 404，订阅也不会生成 gRPC 节点。XHTTP 代码保留，但当前不作为生产节点能力下发。
- 边缘节点只允许签名的 `/__opus8/*` 控制端点和精确匹配的数据通道进入内核；旧 `/login`、`/admin/*`、`/sub`、`/version`、`/locations` 均在读取策略前返回统一 404。
- 用户新增、修改、停用或删除会推进策略版本，并向各节点发送 HMAC 签名的缓存失效通知；通知失败时由 15 秒缓存 TTL 兜底。
- 控制面短时不可达时，节点可继续使用未被失效的最后一份策略；已收到失效版本但无法取得新策略时只保留本地管理员兜底，避免继续放行已吊销用户。
- 节点接口使用 HMAC v2，签名同时绑定时间戳、节点 ID、HTTP 方法、完整路径与查询、原始正文；合法请求不能再跨端点或篡改正文后重放。管理员先预注册 Node ID、Cloudflare Account ID、域名和传输路径，CI 用一次性令牌换取每节点独立密钥；单个节点泄露不能冒充其他节点。轮换采用“新密钥激活—部署验证—收回旧密钥”的无损流程。五分钟仅作为时钟偏差/传输重试窗口，节点状态和租约以签名时间单调更新，用量事件以事件 ID 幂等，不增加逐请求 KV 写入。
- 订阅接口使用 Workers Rate Limiting API：每个订阅令牌 20 次/分钟，单来源宽松上限 120 次/分钟；计数键先用 HMAC 匿名化，不把明文 token 或公网 IP 交给计数器，也不写 KV/D1。自定义订阅域名还可由同一部署脚本配置一条可选 Zone WAF 前置规则。
- 每个节点使用稳定派生的独立 WebSocket 路径；节点注册、base64/Xray、Mihomo、sing-box、健康检查和优选 IP 验收共用 D1 中的 `transport_path`。迁移期可同时接受新路径和旧 `/`，strict 部署后旧路径关闭。

## 运营面板

- 管理站继续由 Cloudflare Pages 承载，无需增加服务器；控制 API 由 Worker 承载，统计数据保存在 D1。
- “运营总览”每 30 秒刷新 24 小时流量、连接数、在线 IP、用户风险、节点流量及落地机健康。
- GitHub Actions 每 10 分钟从外部真实建立 VLESS-over-WebSocket 连接，分别验证 CF 直出和落地/WARP 链路；这与只能证明 Worker 存活的心跳相互独立。
- 节点连续 1–2 次直连失败时标记为降级但仍保留在订阅，连续 3 次失败自动摘除；被摘除节点连续 2 次直连成功后自动恢复。仅落地/WARP 失败只告警，不会摘除所有边缘节点。
- 同一任务会逐台验证已启用落地机的 SOCKS5 认证与出站能力；节点或落地机异常时自动创建/更新一个 GitHub Issue，全部恢复后自动留言并关闭，避免重复刷屏。
- 外部邮件、Telegram、企业微信和通用 webhook 通知均未接入；告警只使用 GitHub Issue，合规门禁未通过时也会静默跳过。
- 用户页支持按状态筛选，并查看在线租约、24 小时 IP 指纹和分节点用量；控制面只返回 HMAC 后 IP 指纹的短标识，不返回原始公网 IP。
- 用户被停用、过期、流量耗尽、同时在线 IP 已满、24 小时 IP 已满或即将到期时，后台会显示明确原因。
- 在线设备/IP 记录和流量统计均可单独重置，停用用户会主动通知四个节点失效策略缓存。
