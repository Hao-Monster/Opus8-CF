# P6.8 边缘入口、安全基线与平台边界

审计日期：2026-07-29

## P6.8.1 已实现：单一边缘入口

边缘 Worker 现在采用“默认拒绝”的前置网关。处理顺序固定为：

1. 已知的 `/__opus8/*` 控制端点由原有 HMAC/端点规则处理；
2. 只有精确命中传输路径的 WebSocket Upgrade 或 POST 才进入 vendor 数据面；
3. 普通 `GET /`、`HEAD /` 返回本地静态状态页，不读 KV、不拉控制面、不执行心跳；
4. `/robots.txt` 和 `/favicon.ico` 本地处理；
5. 其他请求统一返回带安全响应头的 `404`。

明确关闭的旧入口：

| 路径 | 结果 |
|---|---|
| `/login` | 404 |
| `/admin`、`/admin/*` | 404 |
| `/sub` | 404 |
| `/version` | 404 |
| `/locations` | 404 |
| 错误路径上的 WebSocket Upgrade | 404 |
| 未知 `/__opus8/*` | 404 |

这一步不是只隐藏 UI。网关在策略 KV 读取、节点心跳和 vendor 路由之前执行，因此旧登录、旧 KV 管理和旧订阅代码无法被外部请求触达。部署脚本还会在每台节点上线后以 GET、POST 和错误路径 WebSocket 复测上述入口；任一入口不是 404，部署即失败。

默认传输路径仍为 `/`，保持当前 `/?ed=2560` 订阅兼容。可通过 `OPUS8_TRANSPORT_PATH` 设置精确路径，但控制路径 `/__opus8` 及其子路径永远不能作为数据通道；配置非法时数据面失败关闭。变更路径前必须同步改造节点注册表和三种订阅生成器，不能只改 Worker。

## P6.8.2 已实现：控制面 CORS 收口

控制面的全局 `Access-Control-Allow-Origin: *` 已移除。新规则是：

- 只有 `ADMIN_UI_ORIGINS` 中精确配置的 origin 才能跨域访问管理员 API；
- 当前生产值为 `https://opus8cf-admin-openal.pages.dev`；
- 不支持通配符，不会因为生产域名被允许而隐式信任 Pages 预览子域；
- 预检方法只允许 `GET`、`POST`、`PUT`、`PATCH`、`DELETE`，请求头只允许
  `Authorization` 和 `Content-Type`；
- 不启用 cookie credentials，继续使用现有 Bearer JWT；
- 带不可信 `Origin` 的管理员 API 请求在解析密码、JWT 或访问 D1 前返回 403；
- 无 `Origin` 的 GitHub Actions、健康检查和服务端调用保持兼容；
- 节点注册、心跳、准入、用量、UUID 同步、订阅和健康端点不返回任何 CORS 许可；
- 控制面部署会在线验证允许来源、拒绝来源、节点 API 和健康接口四种情况，回归失败即中止。

CORS 只是浏览器边界，不替代 JWT、Cloudflare Access 或节点 HMAC。攻击者可以构造不带
`Origin` 的非浏览器请求，因此管理员鉴权仍是实际安全边界。

## P6.8.3 已实现：HMAC v2 请求绑定与重放收敛

旧签名只覆盖 `timestamp.nodeId.body`，同一份合法签名可能被搬到另一个方法或端点。HMAC v2 的规范化消息改为：

```text
opus8-hmac-v2
<13 位毫秒时间戳>
<node id>
<大写 HTTP method>
<pathname + 原始 query>
<原始 body>
```

当前实现包含以下约束：

- 注册、心跳、UUID 拉取、准入、用量上报、策略失效与策略状态端点全部使用 v2；
- 方法、路径、查询或正文任意一项变化都会导致 401；
- v2 头一旦存在就只验证 v2，错误 v2 不能借有效 v1 头降级；
- 时间戳格式固定为 13 位毫秒，允许前后五分钟时钟偏差；
- 注册和心跳正文的 `nodeId` 必须与签名身份一致；
- 边缘内部 `/__opus8/policy/*` 端点只接受 v2；
- 新节点、节点注册和边缘内部控制端点只接受 v2；v1 不能注册节点，也不能命中带查询参数或未列入白名单的接口；
- 因合规门禁禁止自动重部署现有数据面，控制面仅为策略中明确列出的四个存量节点保留临时 v1 兼容，且只允许心跳、UUID 拉取、准入和用量上报；
- 控制面只向同一存量节点白名单发送 v1/v2 双签名的策略失效通知；兼容期限由
  `infra/compliance-policy.json` 固定为 2027-07-29，不会在每次部署时自动顺延。

系统没有为每个请求写 nonce 到 KV。五分钟窗口内的同端点重复请求改由业务幂等收敛：节点的
`last_seen`、配置和租约只按已签名时间戳单调前进，旧请求不能延长状态；用量事件由稳定事件 ID 去重。
这会允许完全相同的请求再次得到同等语义的响应，但不会重复累计用量或延长租约，也不会消耗高频 KV 写额度。

自动测试覆盖跨端点重放、查询/方法/正文篡改、错误 v2 禁止降级、v1 节点/接口白名单、
截止时间和边缘控制端点拒绝 v1。
部署 smoke 还会在线验证合法心跳为 200，而把同一签名搬到用量端点必须为 401。

## P6.8.4 已实现：订阅原生限流

`GET /sub/<token>` 现在有两层不依赖 KV 的 Workers Rate Limiting：

- 先按来源执行 120 次/分钟的宽松上限，降低随机 token 扫描到达 D1 的数量；
- 再按订阅 token 执行 20 次/分钟的用户级上限；
- 来源和 token 均先以 `NODE_HMAC_SECRET` 做带域分离的 HMAC，Rate Limiting 计数器只接收 64 位摘要；
- token 必须是系统生成的 32 位 URL-safe 格式，否则在 D1 查询前返回 404；
- 达到上限返回 429、`Retry-After: 60` 和 `Cache-Control: private, no-store`；
- 正常订阅同样强制 `private, no-store`，避免含 UUID 的订阅正文进入共享缓存；
- 生产环境绑定缺失或 API 异常时返回 503，不会降级为无限制访问。

Cloudflare 官方说明该 API 在同一数据中心本地计数、异步汇总并允许短时超量，因此这里把它定位成资源保护，
而不是精确账单或全球防分享系统。客户端跨地区共享仍由已有 IP 租约、24 小时 IP 指纹和流量额度处理。

自定义订阅域名还有一条可选的 Zone WAF 前置规则，同样按来源做 120 次/分钟粗限流。WAF 能在 Worker 执行前阻断，
但不覆盖 `workers.dev`，并可能受 Zone 套餐规则数和 API Token 的 `Zone WAF: Edit` 权限影响；配置失败只告警，
Workers 内的强制绑定不会被关闭。

验收覆盖 HMAC 隐私键、来源优先短路、token 429、绑定缺失/异常的 503、非法 token 404、成功响应禁止缓存，
以及本地 Wrangler 4 Rate Limiting binding 的实际阈值触发。生产 smoke 不依赖“第 N 次必须精确拦截”这一错误假设，
只验证强制绑定已调用并返回保护标识。

## P6.8.5 已实现：传输路径平台化

节点表新增 `transport_path`。部署脚本优先复用控制面已注册路径；首次从 `/` 迁移时通过节点 ID 和
`NODE_HMAC_SECRET` 派生 `/ws/<24位摘要>`，并在带 HMAC v2 的注册正文中上报。密钥轮换不会隐式改变
已经注册的路径。控制面拒绝查询参数、路径遍历、重复斜杠和
控制/旧管理入口；数据库中出现非法路径的节点也不会进入订阅。

路径现在贯穿同一条配置链：

1. Worker 的 `OPUS8_TRANSPORT_PATH` 精确决定可进入 vendor 内核的数据通道；
2. 节点注册把完全相同的 pathname 写入 D1；
3. base64/Xray、Mihomo、sing-box 从该字段生成各自格式；
4. 部署 smoke、定时健康检查、优选 IP 双视角探测和 Zero Trust 验收从节点 API 读取该字段；
5. 管理站节点页显示当前路径，运营人员可核对迁移状态。

Early Data 与 pathname 分开建模。Xray URI 使用官方兼容的 `?ed=2560`；Mihomo 和 sing-box 使用
各自的 `max-early-data`/`max_early_data` 与 `Sec-WebSocket-Protocol` 字段，不再把 Xray 的
查询参数机械复制到所有格式。

首次迁移使用 `canary`：新路径上线后，Worker 在 72 小时内同时接受上一条路径（首次为 `/`），从而覆盖“Worker 已更新、
节点尚未注册”和“客户端尚未刷新订阅”两个窗口。主路径配置非法时整个数据面失败关闭，不会退回旧路径；
宽限到期或 `strict` 部署后 `/` 自动返回 404。旧路径只用于有时限的迁移，不是长期双入口。
持久迁移模式由 `infra/transport-mode.txt` 管理；手动工作流参数只覆盖一次运行，防止后续自动部署把
已经关闭的旧路径重新打开。

路径随机化不是匿名或规避平台检测的安全边界。它减少所有节点共用 `/?ed=2560` 带来的通用错误路径暴露，
但 WebSocket 的 HTTP/1.1/Upgrade 特征仍然存在；是否迁移 XHTTP 属于后续独立实验。

自动验收覆盖保留路径、查询/遍历/重复斜杠拒绝、新旧双路径宽限与过期、D1 单一来源、四种订阅字段、
真实本地 Worker 集成，以及健康/优选/Zero Trust 脚本的动态路径读取。

## P6.8.6 已实现：真实客户端兼容矩阵

十分钟健康检查继续使用无第三方依赖的 VLESS 协议探针覆盖每个已启用节点；它适合高频判断节点是否可用，
但不能证明第三方客户端的新版本仍接受我们的订阅。新增的 `client-compatibility` 工作流负责第二层验收：

- 固定 Xray `26.3.27`、Mihomo `1.19.29`、sing-box `1.13.15` 的 Linux amd64 官方发布物和
  SHA-256，不使用浮动的 `latest`；
- 每周一次或手动运行，只选择一台 `healthy` canary；运营人员也可输入节点 ID 做定向复测；
- 为 canary 创建短期隔离用户，分别拉取 base64、Xray、Mihomo 和 sing-box 订阅；
- 在启动客户端前交叉验证四种格式的节点数量、地址、UUID、443 端口、SNI、Host、WebSocket pathname 和
  Early Data，并拒绝任何跳过证书校验的配置；
- 调用三个客户端自身的配置检查，再通过各自本地 SOCKS 入站发起真实 HTTPS 请求；
- 要求控制面的连接数至少增加 3，且上下行用量都大于 0，证明边缘遥测不是“配置能解析但没有数据”；
- `trap` 在所有退出路径终止进程、删除隔离用户和精确的 `/tmp/opus8-client-compat.*` 目录。

v2rayN 使用的 base64 VLESS URI 会被严格解析，实际链路由它所使用的 Xray 核心完成；Windows GUI 导入仍保留为
桌面客户端发版时的人工抽查项。自动矩阵不会部署节点、改变健康状态、跨账号恢复或发出外部通知。

版本升级必须先从 GitHub Release API 确认稳定 release 和资产摘要，更新
`infra/client-compatibility.json` 后通过静态配置测试，再手动运行真实矩阵。一次运行只创建/删除一个
D1 canary 用户并写入三条以上用量，不新增 KV 计数器或外部告警状态。

## 客户端安全基线

### Xray / v2rayN

- 保持 `allowInsecure=false`，SNI 必须是节点证书域名。
- VLESS-over-WebSocket 保持 HTTP/1.1 兼容，不强行只声明 `h2`。Xray 官方说明 WebSocket/HTTPUpgrade 默认使用 `http/1.1`，协商到 `h2` 反而可能导致连接失败。
- 保留稳定的 `fp=chrome` 兼容值，但不实施“按 UUID 随机浏览器指纹”。Xray 官方明确说明 uTLS 只模拟 ClientHello，不能复制完整浏览器行为；无依据的随机化可能制造更多异常组合。
- Browser Dialer 和 XHTTP 只进入隔离实验，不直接面向全部用户下发。

参考：[Xray TLS 官方文档](https://xtls.github.io/en/config/transports/tls.html)。

### Mihomo

- 保持 `tls: true`、正确 `servername` 和 `client-fingerprint: chrome`。
- 不输出 `skip-cert-verify: true`。
- WebSocket 配置不硬编码 `alpn: [h2]`；Mihomo 官方说明 ALPN 无共同协议时连接会失败。
- 不使用分析报告建议的 per-UUID 随机指纹池。客户端能力、TLS 实现和版本必须先通过兼容矩阵验证。

参考：[Mihomo TLS 官方文档](https://wiki.metacubex.one/en/config/proxies/tls/)。

### sing-box

- sing-box 订阅已经移除 `utls.enabled` 和伪造浏览器指纹，使用系统 TLS，明确输出 `insecure: false`。
- 原因是 sing-box 官方将 uTLS 标为“不推荐”，并说明仅复制 ClientHello 无法复制浏览器 TLS 栈行为且仍可能被识别。
- ECH、TLS fragment 和 record fragment 不作为默认“抗检测开关”。官方同样提醒 fragment 不应被视为对真实审查系统的通用方案。

参考：[sing-box TLS 官方文档](https://sing-box.sagernet.org/configuration/shared/tls/)。

## Cloudflare 合规与工程边界

截至审计日，Cloudflare Self-Serve Subscription Agreement 第 2.2.1(j) 已明确要求：
除非获得 Cloudflare 书面许可，不得使用其服务提供 VPN 或类似代理服务。Developer Platform
专用条款还增加了以下产品约束：

- Cloudflare 可在请求造成过度负担、影响服务或网络完整性时限制请求或存储；
- 对涉嫌违反协议的 Developer Platform 使用，Cloudflare 可限制或暂停；
- 使用者对终端用户行为负责，并必须遵守开发文档和第三方条款；
- Workers TCP Socket 虽是官方 API，但官方限制连接 Cloudflare IP、localhost、私网地址、自环和 25 端口，并计入并发连接限制。

参考：[Cloudflare Developer Platform 专用条款](https://www.cloudflare.com/service-specific-terms-developer-platform/)、
[Workers TCP Sockets 官方文档](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/)。

据此确定以下红线：

- 不把多账号部署用于绕过配额、暂停或滥用处置；
- 不做“检测到封禁后自动换账号/换域名继续”的规避链路；
- 节点异常只自动摘除和告警，恢复、迁移或重新部署需要人工确认原因并留痕；
- 在任何新增用户、节点部署或显著放量前，先取得 Cloudflare 对本项目具体形态的书面许可；
- 保留用量、错误率、并发连接、异常目的端口和投诉处理记录。

## 关于 GFW/网络检测的判断

仓库中的旧分析把“静态伪装首页”“随机 TLS 指纹”“XHTTP 一定更抗检测”等结论写得过于确定。这些结论缺乏项目自身的多网络、长周期对照数据，也不能从上述客户端官方文档推出。

当前策略是减少暴露面和协议异常，而不是承诺不可检测：

- 状态页只用于正常 HTTP 语义、最小信息披露和避免旧入口暴露，不伪造第三方品牌或真实业务；
- 路径由严格网关控制，路径随机化不是安全边界；
- 保持客户端官方支持的 TLS、SNI、证书校验和 WebSocket ALPN 组合；
- 将连接成功率、握手阶段、HTTP 状态、首包时间按“节点 × 客户端 × 网络视角”记录；
- XHTTP、ECH 或其他传输只有在受控 canary 中显著改善且不增加错误率时，才进入下一轮审计。

## 上线与回滚

上线顺序：

1. 本地执行边缘策略测试、边缘构建、控制面类型检查和构建；
2. 只部署一台 canary 节点；
3. 验证根状态页、旧入口 404、`/__opus8/build`、合法 VLESS-WS、错误 UUID 拒绝；
4. 观察至少一个健康检查周期；
5. 再逐台部署，其间保留至少一台旧节点供客户端回退。

回滚节点构建时不要删除 `nodes.transport_path`；在迁移期可重新以 `canary` 部署，让旧 `/` 临时恢复并重新生成旧格式订阅。若仅 sing-box 客户端出现兼容问题，可先回滚控制面订阅构建而不回滚边缘网关。任何回滚都不得重新开放 vendor 旧管理入口。
